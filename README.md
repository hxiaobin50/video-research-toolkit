# 视频调研工具包（内部版）

这是一个面向公司内部、Windows 与 Codex 的通用视频调研插件。使用者只需用自然语言说明“想研究什么”，Codex 会选择对应的 Skill，完成所需的采集、整理、分析和文件输出。

工具不绑定轮毂轴承或任何固定品类，也不会每次都生成一整套无关文件。

> 当前版本：`0.1.0`（内部试用版）
>
> 适用环境：Windows + Codex
>
> 默认输出：Excel 和 Markdown；不默认生成 HTML

## 一、这个工具适合做什么

它可以帮助你回答四类常见问题：

1. **研究应该怎么开始？**——明确范围、建立搜索词、完成小样本试跑。
2. **各平台上的视频都在讲什么？**——分析内容供给、主题、旅程阶段、表现数据和优秀样本。
3. **观众在评论区真正关心什么？**——分析 VOC、需求、异议、旅程证据和内容信任反馈。
4. **这些信息最终说明了什么？**——把已有证据整理成可追溯、可讨论、可落地的 Markdown 报告。

工具支持 YouTube、TikTok、Instagram 等平台，在同一项目中复用已经采集的数据，并支持中断后继续。

第一版不包含网页界面、固定品类分类或固定消费者旅程，也不默认延伸到品牌定位、拍摄脚本、内容排期、广告投放、销售归因或完整 GTM。

## 三、5 个 Skill 分别能做什么

### 先看这张选择表

| Skill | 什么时候使用 | 主要分析内容 | 默认输出 |
|---|---|---|---|
| `video-research` | 想做完整调研，或还不确定该调用哪个 Skill | 判断任务范围，调度一个或多个专用 Skill，复用已有数据并衔接进度 | 只输出本次实际需要的文件 |
| `video-research-design` | 刚开始一个项目，需要明确范围、搜索词或先试跑 | 研究边界、搜索词、动态扩词、初始旅程假设、数据可得性和小样本质量 | `00_研究设计与证据计划_Research_Design.xlsx` |
| `video-content-landscape` | 想知道平台上有哪些视频、都在讲什么、什么内容表现较好 | 相关性、内容主题、旅程阶段、用户任务、时长、互动率、相对表现和人工观看样本 | `01_视频内容调研_Video_Landscape.xlsx` |
| `video-comment-voc` | 想研究评论区的需求、问题、异议或信任反馈 | 逐条评论语义、用户任务、需求、旅程证据、VOC主题和内容信任 | `02_评论VOC分析_Comment_VOC.xlsx` |
| `video-research-report` | 已有调研数据，需要形成正式结论 | 综合视频供给、表现、VOC、旅程、信任、反例、限制和机会点 | `03_视频调研分析报告_Video_Research_Report.md` |

### 1. `video-research`：完整项目协调

**什么时候使用**

- “从头完成一次完整的视频调研。”
- “我不确定应该先做内容调研还是 VOC，请帮我安排。”
- 一个任务同时涉及研究设计、视频内容、评论和最终报告。

**会做什么**

- 理解研究目的和已有资料；
- 判断需要调用哪些专用 Skill；
- 复用已经采集和分析过的数据；
- 按合理顺序衔接多个阶段；
- 只生成当前范围需要的交付物。

**不会做什么**

- 不会因为调用了协调 Skill 就强制生成全部文件；
- 不会自动把视频调研扩展成品牌策略、拍摄方案或营销计划。

### 2. `video-research-design`：项目配置、搜索词与试跑

**什么时候使用**

- 研究刚开始，还没有清晰的搜索方案；
- 已有一些关键词，但担心旅程覆盖不全；
- 想先测试各平台能否获得有效数据；
- 想判断哪些搜索词值得进入正式采集。

**会做什么**

- 明确研究对象、市场、语言、平台、时间范围和研究问题；
- 根据品类表达、用户任务、旅程线索、问题词、推荐词和评测词等生成初始搜索词；
- 不使用固定搜索词分类，允许根据项目增加“种草词”等自定义方向；
- 用小样本检查相关性、重复度、字段完整性、评论可用性和预计付费调用；
- 根据试跑结果保留、修改、停止或扩展搜索词；
- 将初始消费者旅程作为“待验证假设”，供后续视频和 VOC 数据共同校准。

**默认交付物**

`00_研究设计与证据计划_Research_Design.xlsx`，包含：

- `00_项目配置_Project_Config`
- `01_研究问题_Research_Questions`
- `02_搜索词_Search_Queries`
- `03_搜索试跑_Search_Pilot`
- `04_旅程假设_Journey_Hypothesis`

**不会做什么**

- 试跑结束后不会自动开始大规模正式采集；
- 不会把预测的消费者旅程当成最终结论。

### 3. `video-content-landscape`：视频内容生态调研

**什么时候使用**

- 想了解一个品类在多个视频平台上的内容现状；
- 想比较长视频与短视频分别在讲什么、哪些内容表现较好；
- 想寻找值得完整观看和学习的优秀视频；
- 已有视频链接或视频清单，希望统一整理和分类。

**会做什么**

- 统一整理 YouTube、TikTok、Instagram 等平台可获得的公共视频信息；
- 对每条视频做相关性审核和内容语义分类；
- 记录主要旅程阶段、次要旅程阶段和该阶段要解决的主要任务；
- 按 `0–30秒`、`31–60秒`、`61–120秒`、`120秒以上` 形成时长分组；
- 在平台提供相应数据时计算点赞率、评论率、分享率和收藏率；
- 在同平台、同类可比较样本中解释相对表现，不把跨平台数字强行排成一个榜单；
- 选择优秀长视频、优秀短视频和确实无法可靠判断的视频进入人工观看；
- 对人工观看样本记录实际观察和有价值的时间点。

**默认交付物**

`01_视频内容调研_Video_Landscape.xlsx`，包含：

- `00_项目配置_Project_Config`
- `01_搜索词_Search_Queries`
- `02_视频主表_Video_Master`
- `03_人工观看_Manual_Review`

**不会做什么**

- 不会自动分析评论 VOC；
- 无法从公开接口获得的数据不会被推测补齐，例如大多数平台的完播率；
- 不会只因为 AI 难以判断就把大量视频推给人工观看。

### 4. `video-comment-voc`：评论 VOC 调研

**什么时候使用**

- 想知道用户在视频评论区提出了哪些问题、需求和异议；
- 想用评论证据校准消费者旅程；
- 想分析用户为何信任或不信任一条视频、讲解者或演示方式；
- 只想研究指定视频的评论，不需要重新做视频内容生态。

**会做什么**

- 先逐条理解原始评论，再归纳主题，避免只看关键词造成误判；
- 区分评论原意、用户任务、核心需要、异议、情绪和可能影响的判断；
- 记录评论对既有消费者旅程的支持、修正或新增建议，而不是再创建一套独立旅程；
- 将与旅程关系不大的内容反馈单独纳入“内容与信任”分析，例如信息是否清楚、演示是否可信、拍摄是否便于理解、讲解者是否专业、是否存在广告怀疑或错误纠正；
- 汇总评论数量与不同视频数量，同时保留代表性原话、反对意见和反例；
- 让汇总结论可以回到具体评论和原视频。

**默认交付物**

`02_评论VOC分析_Comment_VOC.xlsx`，包含：

- `00_项目配置_Project_Config`
- `01_视频来源_Video_Sources`
- `02_原始评论_Raw_Comments`
- `03_逐条理解_Comment_Analysis`
- `04_VOC主题_VOC_Themes`
- `05_旅程证据_Journey_Evidence`
- `06_内容信任_Content_Trust`

**不会做什么**

- 不会自动生成视频内容主表；
- 不会把点赞数直接解释为购买意向或市场需求强度；
- 不会把所有评论强行归入消费者旅程。

### 5. `video-research-report`：证据型 Markdown 报告

**什么时候使用**

- 已经完成视频内容或评论 VOC 调研，需要一份正式分析；
- 想围绕一个较窄的问题生成专项报告；
- 希望把不同 Excel 和原始证据连接成完整结论。

**会做什么**

- 检查现有证据是否足以回答研究问题；
- 根据需求分析内容供给、平台表现、消费者旅程、VOC、内容信任和人工观看发现；
- 寻找共性、差异、缺口、矛盾证据和可能的其他解释；
- 区分“数据直接支持”“基于证据的推断”和“仍需验证”；
- 形成有观点、有证据、有边界和可落地建议的报告；
- 使用可点击链接关联原视频或其他原始证据；
- 仅在确实改善阅读时加入表格或图表。

**默认交付物**

`03_视频调研分析报告_Video_Research_Report.md`

**不会做什么**

- 不会为了补报告而静默发起新的付费采集；
- 不会把 Excel 简单换一种格式重复罗列；
- 不会在证据不足时伪造完整结论。

## 四、Skill 之间如何衔接

完整调研通常按下面的逻辑推进：

```text
研究设计与搜索试跑
        ↓
视频内容生态调研
        ↓
评论 VOC 调研
        ↓
Markdown 综合报告
```

这不是强制流程。使用者可以直接调用其中任何一个 Skill：

- 已经有视频清单，可以直接做视频内容调研；
- 只想研究几个指定视频的评论，可以直接做 VOC；
- 已经有完整数据，可以直接生成报告；
- 只有在请求“完整调研”时，协调 Skill 才会组合多个阶段。

各 Skill 通过同一个项目目录中的配置和状态文件交接，因此后续 Skill 能知道前面已经完成什么、数据保存在哪里、哪些请求无需重复付费。

## 五、自然语言调用示例

### 只做研究设计和搜索试跑

```text
我要研究[研究对象]在[目标市场]的视频内容。请先建立项目配置、生成搜索词并做小样本试跑，不要开始正式采集。
```

### 只做视频内容调研

```text
请调研YouTube、TikTok和Instagram上[研究对象]的视频都在讲什么，比较长短视频的内容和表现，并筛选值得完整观看的优秀样本。不要分析评论VOC。
```

### 只做评论 VOC

```text
请分析当前项目已有视频的评论VOC，重点理解用户需求、异议、旅程证据，以及用户对内容和讲解者的信任反馈。不要重新做视频内容主表。
```

也可以限定指定视频：

```text
请只分析以下视频的评论VOC：[粘贴视频链接]。如果评论不可获取，先说明情况并给我可选方案，不要自行换成其他视频。
```

### 只生成报告

```text
请根据当前项目已有数据生成Markdown视频调研报告，不要重新采集。结论需要关联真实证据，并写清反例、限制和仍需验证的内容。
```

### 从头完成完整调研

```text
请从头完成一次[研究对象]在[目标市场]的完整视频调研，平台包括[平台]，最终输出研究设计、视频内容、评论VOC和Markdown综合报告。开始前只询问会实质影响研究的缺失信息。
```

Excel 是基础参考格式。使用者可以根据项目需要增加或调整业务分析字段；工具会保留用于数据追溯、去重和阶段交接的系统字段。

## 六、API 配置

插件不会内置或保存任何人的真实 API Key。每位使用者使用自己的 Key，并将其保存在自己的研究项目目录中。

首次调用需要采集的平台时，Codex 会提示使用者：

1. 将插件中的 `.env.example` 复制到本次研究项目目录；
2. 将文件改名为 `.env`；
3. 只填写本次需要使用的平台 Key。

```text
YOUTUBE_API_KEY=你的Key
SCRAPECREATORS_API_KEY=你的Key
```

- YouTube 数据使用 `YOUTUBE_API_KEY`；
- 由 ScrapeCreators 支持的平台使用 `SCRAPECREATORS_API_KEY`；
- 不调用的平台不需要提前配置；
- 不要将 `.env` 发给他人、上传 GitHub 或粘贴到 Codex 对话中；
- Codex 只检查 Key 是否存在和接口是否可用，不应在回复、日志或交付物中显示完整 Key。

## 七、运行时会生成什么

使用者开始一个研究项目后，工具会在指定的项目目录中管理以下内容：

```text
项目目录/
├── project-config.json          # 研究对象、市场、平台、日期和范围
├── .env                         # 使用者自己的API Key，不上传、不分享
├── .video-research/
│   ├── state.json               # 已完成阶段、文件位置和中断位置
│   ├── cache/                   # 已请求过的数据，避免重复请求
│   └── logs/                    # 运行记录和API调用结果
├── raw/                         # 平台返回的原始数据
├── processed/                   # 清洗、统一字段和去重后的数据
└── outputs/                     # 本次要求生成的Excel或Markdown文件
```

这些内部文件主要由工具自动处理。使用者通常只需要查看 `outputs` 中的交付物，并校对研究范围、分类、语义解释和最终结论。

## 八、工具自动处理的规则

- **原始数据保护：**原始数据与分析结果分开保存，不覆盖原始证据；
- **清洗与统一：**将不同平台字段整理为统一结构，同时保留平台差异；
- **去重：**优先按平台内容 ID 和评论 ID 去重，并保留同一内容的多个发现来源；
- **缓存：**调用前检查已经保存的数据，避免对同一请求重复付费；
- **续跑：**采集中断后记录完成位置，恢复时从未完成部分继续；
- **缺失值：**区分“平台未提供”“请求失败”“没有数据”和“该字段不适用”；
- **重试：**先判断失败原因；涉及额外付费请求时，在重试前询问使用者；
- **额度：**能够读取余额时，在剩余约 25% 时提醒使用者；无法精确读取时按已知调用量提示风险，不伪造余额；
- **版本与追溯：**记录采集时间、搜索词、采集批次、Prompt/规则版本和来源链接；
- **输出检查：**检查文件是否存在、字段是否完整、证据能否追溯，并扫描是否意外写入密钥。

## 九、使用者需要校对什么

使用者不需要读代码。建议重点校对：

1. 项目范围、研究问题和搜索词是否符合真实业务；
2. 初始消费者旅程是否遗漏关键阶段；
3. 视频相关性、内容分类和主要任务是否符合该品类；
4. 人工观看样本是否真的优秀，或是否确实存在判断困难；
5. 评论原意、VOC主题和内容信任解释是否准确；
6. 报告结论是否有足够证据、是否考虑反例、是否能够落地。

如果使用者修改了 Excel 的业务字段，应在继续下一阶段时告诉 Codex，以便后续分析沿用新定义。

## 十、准确性和使用边界

- 公开播放、点赞、评论、分享和收藏数据只能反映可观察的内容互动，不能直接证明销量、转化或因果关系；
- 大多数平台不会通过公开接口提供完播率，工具不会用其他指标冒充完播率；
- 不同平台的统计口径和可用字段不同，应分别解释；
- AI 可以完成大部分相关性、分类和评论语义判断，但关键业务定义及高影响结论仍需使用者校对；
- 指定视频没有字幕或评论时，工具会说明原因并提供选择；非指定样本则优先更换为可分析的视频；
- 原始链接、采集时间和证据 ID 会被保留，便于复核。

## 十一、关于中英文

Skill 的内部指令目前使用英文，是为了与 Codex、API 字段及英文研究材料保持一致；README 使用中文，方便团队成员理解和调用。

Skill 写成中文本身不会必然降低 Codex 的准确性。真正影响结果的是规则是否明确、字段定义是否一致、证据边界是否清楚以及是否经过验证。因此，当前采用“**英文内部指令 + 中文使用说明 + 双语交付字段**”的方式。使用者无需阅读英文 Skill 文件，也不需要依赖浏览器翻译才能正常使用。
